# Лабораторная работа. Сервис тикетов техподдержки

**Уроки 5 и 6 · FastAPI**

## 1. Задача

Разработайте внутренний сервис техподдержки **HelpDesk Lite**. Сотрудник компании создаёт тикет с описанием проблемы, а команда поддержки назначает исполнителя, меняет приоритет и переводит тикет по этапам обработки.

Дополните выданный каркас: реализуйте хранение тикетов, бизнес-логику и незавершённые эндпоинты. Готовое приложение должно создавать, показывать, изменять и удалять тикеты, а также выдавать список с сортировкой и пагинацией.

Все группы выполняют одно задание. Распределите работу самостоятельно; каждый участник должен понимать решение группы.

## 2. Подготовка и запуск

Потребуются Python 3.10 или новее, FastAPI, Pydantic 2 и Uvicorn. В комплект входят:

- `starter.py` - модели, настройки, исключения, зависимости и каркас приложения;
- `requirements.txt` - зависимости для установки;
- условие работы в Markdown и PDF.

Создайте папку проекта и поместите в неё `starter.py` и `requirements.txt`. Откройте терминал в этой папке.

```bash
python -m venv .venv
```

Активируйте окружение. На Linux и macOS:

```bash
source .venv/bin/activate
```

На Windows в командной строке cmd:

```bat
.venv\Scripts\activate.bat
```

Установите зависимости и запустите приложение:

```bash
python -m pip install -r requirements.txt
python -m uvicorn starter:app --reload
```

Откройте Swagger UI: [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs). В исходном каркасе документация открывается, но незавершённые операции завершаются `NotImplementedError`. Замените все такие заглушки своей реализацией.

Каждая группа запускает собственный процесс. Данные хранятся в памяти и исчезают при перезапуске, в том числе после перезагрузки приложения из-за изменения кода.

## 3. Контракт данных

Модели уже заданы в `starter.py`: `TicketCreate`, `TicketUpdate`, `Ticket` и `TicketPage`. Сохраните их поля и назначение.

### Создание тикета

| Поле запроса | Правило |
| --- | --- |
| `title` | Обязательная строка длиной не менее одного символа. |
| `description` | Необязательная строка; по умолчанию `null`. |
| `priority` | `low`, `normal`, `high` или `urgent`; по умолчанию `normal`. |
| `assignee` | Необязательная строка с именем исполнителя; по умолчанию `null`. |

Сервер назначает `id`, `status` и `created_at`. Новый тикет всегда имеет статус `open`. Идентификатор - положительное целое число; в пределах одного запуска удалённые идентификаторы повторно не используются. В `created_at` сохраняется время создания; при обновлении оно не меняется.

### Частичное обновление

Через `PATCH` можно менять только `description`, `priority`, `assignee` и `status`. Поля `id`, `title` и `created_at` остаются прежними.

Для этой работы действуют следующие правила:

- отсутствующее поле и явный `null` означают «оставить прежнее значение»;
- пустой объект `{}` возвращает текущий тикет без изменений;
- дополнительные поля, которых нет в модели запроса, игнорируются, как в выданном каркасе;
- если изменение отклонено, ни одно поле сохранённого тикета не должно измениться.

## 4. Переходы статуса

Допустимые значения: `open`, `in_progress`, `resolved`, `closed`. Переходы уже заданы в `ALLOWED_TRANSITIONS`.

| Текущий статус | Разрешённый новый статус |
| --- | --- |
| `open` | `in_progress` |
| `in_progress` | `resolved` или `open` |
| `resolved` | `closed` или `in_progress` |
| `closed` | Переходов в другой статус нет. |

Проверяйте переход относительно **сохранённого** статуса. Повторная передача текущего статуса допустима и не считается переходом. Неизвестное значение статуса отклоняется валидацией с кодом `422`, а известный, но запрещённый переход - с кодом `409`.

Статус `closed` запрещает только переход в другой статус. Остальные разрешённые поля можно изменять. Удаление разрешено для тикета в любом статусе.

## 5. HTTP API и ошибки

| Метод и путь | Результат успешного запроса |
| --- | --- |
| `POST /tickets` | `201`, созданный `Ticket`. |
| `GET /tickets` | `200`, страница `TicketPage`. |
| `GET /tickets/{ticket_id}` | `200`, найденный `Ticket`. |
| `PATCH /tickets/{ticket_id}` | `200`, обновлённый `Ticket`. |
| `DELETE /tickets/{ticket_id}` | `204`, без тела ответа. |

Для отсутствующего тикета операции получения, изменения и удаления возвращают `404`. Запрещённый переход статуса возвращает `409`. Оба ответа содержат JSON с пояснением в поле `detail`; точная формулировка сообщения может отличаться.

```json
{"detail": "Тикет 42 не найден"}
```

```json
{"detail": "Переход open -> closed запрещён"}
```

Ошибки входных данных возвращаются как `422`: например, пустой `title`, неизвестный приоритет, недопустимое поле сортировки или `page=0`.

## 6. Сортировка и пагинация

Параметры запроса `GET /tickets`:

| Параметр | Допустимые значения и значение по умолчанию |
| --- | --- |
| `sort_by` | `created_at` или `priority`; по умолчанию `created_at`. |
| `order` | `asc` или `desc`; по умолчанию `desc`. |
| `page` | Целое число от 1; по умолчанию 1. |
| `page_size` | Целое число от 1; без параметра берётся из настроек. |

Сначала отсортируйте **весь список**, затем выберите страницу. В одном запросе используется одно поле сортировки. Для приоритета порядок возрастания такой: `low < normal < high < urgent`; порядок убывания обратный. При равных значениях допустимо сохранить порядок создания.

Настройки уже заданы: `default_page_size = 5`, `max_page_size = 20`. Если запрошенный размер больше максимума, используйте максимум. Например, `page_size=100` даёт размер страницы 20, а не ошибку. Настройки нужно читать из `Settings`, а не дублировать числа в сервисе.

Ответ `TicketPage` содержит `items`, `total`, `page` и `page_size`. В `total` верните количество всех тикетов до пагинации, в `page_size` - фактически использованный размер. Для страницы за пределами списка верните `200` и пустой `items`; `total` остаётся прежним.

## 7. Что реализовать

### Репозиторий

`TicketRepository` хранит тикеты в `self._tickets`. В этой работе используется словарь `dict[int, Ticket]`, уже заданный в каркасе.

| Метод | Назначение |
| --- | --- |
| `add(ticket)` | Сохранить новый тикет и вернуть его. |
| `get(ticket_id)` | Вернуть тикет или поднять `TicketNotFoundError`. |
| `list_all()` | Вернуть список сохранённых тикетов. |
| `update(ticket)` | Заменить существующий тикет и вернуть его; при отсутствии поднять `TicketNotFoundError`. |
| `delete(ticket_id)` | Удалить тикет; при отсутствии поднять `TicketNotFoundError`. |

Метод `next_id()` уже реализован. Репозиторий не проверяет переходы статуса, не знает об HTTP-кодах и не формирует `JSONResponse`. Использовать модель `Ticket` для хранения данных разрешено.

### Сервис

`TicketService` получает репозиторий и настройки через конструктор. Допишите три метода:

- `create_ticket` - сформировать тикет с серверными полями и сохранить его;
- `list_tickets` - применить настройки размера страницы, сортировку и пагинацию, вернуть `TicketPage`;
- `update_ticket` - получить тикет, проверить переход статуса, применить допустимые изменения и сохранить результат.

Методы `get_ticket` и `delete_ticket` уже вызывают репозиторий. Проверку запрещённого перехода выполняйте **до изменения сохранённых данных**. При нарушении правила поднимайте `InvalidStatusTransitionError`.

### Эндпоинты, зависимости и настройки

Допишите тела эндпоинтов создания, списка и обновления: каждый передаёт параметры одному методу сервиса и возвращает результат. Поиск, сортировка и проверки статуса должны оставаться вне эндпоинтов.

Сохраните готовую цепочку `Depends`: настройки и репозиторий передаются в сервис, сервис - в эндпоинты. Репозиторий должен быть общим для запросов одного процесса. Обработчики `TicketNotFoundError` и `InvalidStatusTransitionError` уже зарегистрированы; не заменяйте их на `HTTPException` внутри сервиса или репозитория.

У каждого эндпоинта сохраните `tags`, `summary` и правильный HTTP-код. Для ответов с данными нужен `response_model`; у `DELETE` с кодом `204` тела и модели ответа нет. О значении кода `204` см. [документацию FastAPI](https://fastapi.tiangolo.com/tutorial/response-status-code/).

Можно оставить приложение в одном `starter.py`. Разбиение на модули, база данных, Docker, внешние API, авторизация и тесты на pytest не требуются. Здесь `Settings` - обычная модель с настройками в коде; подключать `.env` не нужно.

## 8. Самопроверка

Запустите приложение и выполните сценарий через Swagger UI или curl. После каждой ошибки убедитесь, что приложение продолжает отвечать.

1. Создайте не менее шести тикетов с разными приоритетами. Проверьте `201`, уникальные ID, статус `open` и заполненное `created_at`.
2. Запросите список без параметров. Проверьте сортировку по дате по убыванию, `page=1`, `page_size=5` и `total`, равный числу созданных тикетов.
3. Проверьте `sort_by=priority` с `order=asc` и `order=desc`. Порядок должен соответствовать важности, а не алфавиту. Проверьте также оба направления для `created_at`.
4. Запросите `page=2&page_size=2`. Ожидаются третий и четвёртый тикеты из отсортированного списка, прежний `total`, `page=2` и `page_size=2`.
5. Проверьте `page_size=100`: в ответе `page_size=20`. Затем запросите заведомо далёкую страницу: `items` пуст, код `200`.
6. Измените одно поле тикета. Остальные поля, включая `id` и `created_at`, должны сохраниться. Проверьте `{}` и `{"description": null}`: они не меняют данные.
7. Проведите тикет по цепочке `open -> in_progress -> resolved -> closed`. Проверьте разрешённые возвраты `in_progress -> open` и `resolved -> in_progress` на других тикетах.
8. Для тикета в статусе `open` отправьте показанный ниже PATCH. Ожидается `409`. Повторный GET должен вернуть прежние статус и исполнителя.
9. Удалите тикет: ожидается `204` и пустое тело. GET, PATCH и повторный DELETE по тому же ID должны вернуть `404`.
10. Проверьте невалидные запросы: `title=""`, `priority="unknown"`, `status="unknown"`, `sort_by=title`, `order=up`, `page=0`, `page_size=0`. Ожидается `422`.

Пример запрещённого изменения для шага 8:

```http
PATCH /tickets/1
Content-Type: application/json

{
  "assignee": "Анна",
  "status": "closed"
}
```

Подставьте ID своего тикета, который находится в статусе `open`.

Дополнительно убедитесь, что повторная передача текущего статуса допустима, а для `closed` можно изменить исполнителя и удалить тикет, но нельзя вернуть другой статус.

## 9. Критерии готовности

- Приложение запускается, `/docs` открывается, все пять операций доступны.
- Поля и ограничения моделей соответствуют условию; серверные поля формируются корректно.
- CRUD работает, отсутствующий тикет даёт `404`, удаление возвращает `204` без тела.
- Переходы проверяются по таблице; запрещённый переход даёт `409` и не меняет данные.
- Сортировка выполняется до пагинации; настройки, `total` и границы страниц учитываются.
- Хранение находится в репозитории, бизнес-логика - в сервисе, эндпоинты только связывают HTTP с сервисом.
- Собственные исключения преобразуются в HTTP-ответы общими обработчиками; зависимости сохраняют данные между запросами.
- Контракт описан, участники могут объяснить решение.
